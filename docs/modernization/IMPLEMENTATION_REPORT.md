## Status

**PARTIAL; NO-GO for vehicle programming or hardware deployment.** This revision changes ELC source only. It has not been built with an STM32F103 toolchain or run on a board. No ZGW, F93, FCD, or CM5 files or devices were changed. No flashing, erase, reboot, commit, or push occurred.

## Remaining integration defects

1. **Routing blocks end-to-end diagnostics.** ZGW `BSW/Diag/Dcm/Dcm_Cfg.c` and `APP/ParallelFlashSwc/ParallelFlashSwc.c` route ELC logical address `0x58` over extended-address CAN on `0x710`. ELC APP/FBL still accept standard ID `0x702`, respond on `0x703`, and read PCI from byte 0. Neither repository shows a verified translation bridge. `PARALLELFLASHSWC_FORWARD_ASSUME_CAN_FC` is true and the gateway records synthetic transmit acknowledgments; those acknowledgments do not establish ECU acceptance. A ZGW route/PDU change or a tested ELC extended-address transport is required. Document the selected route in both projects, then verify with a physical CAN trace.
2. **FCD programming routines still differ.** FCD's source sends `31 01 0200 02` (select FBL), `31 01 0155` (enter RAM updater), and `31 01 0001 [addr_be32] [size_be32]` (erase); optional separate CRC uses RID `0002`. ELC still implements entry `0007`, application erase `0004`, RAM erase `0006`, and legacy CRC `0000`. Matching `37` CRC does not make the complete FCD sequence usable. An ELC-specific FCD target profile or strictly range-checked ELC routine aliases must be specified and implemented before flashing.
3. **Power-loss recovery is incomplete.** A partially written application can contain plausible vectors before its CRC is stored. Boot validation checks vectors but not a durable, image-length-aware validity record. The RAM self-updater can leave the resident FBL incomplete if interrupted. Neither state is hardware tested. Do not rely on automatic boot or rollback after interrupted programming.
4. **Other network signals remain incompletely verified.** VehicleState and battery payloads were source-correlated to the ZGW DBC and corrected in ELC, but CAN bitrate, actual scheduler timing, gateway receive deadlines, `0x6F7` confidence mapping, and a bench trace remain open. ELC's checked-in `ZGW_CAN_3.dbc` conflicts with the ZGW copy; current ZGW COM source/DBC was used for this revision.
5. **Coding and diagnostics remain incomplete.** The APP has existing DID and NvM handlers, but no verified FCD ELC coding profile, positive/negative-response matrix, session transition, reset/reconnect timing, or DoIP-to-CAN correlation. FCD's checked-in ELC target is simulated and unselected.

F93 `DMU - Digital Main Unit/DMU_FBL/Core/Src/main.c` uses `0x702/0x703` too; its simpler loader is only an implementation reference and does not resolve the current ZGW route or STM32F103 memory rules.

## Current continuation: network and application integration (2026-10-18)

### ZGW/ELC network contract

The source-verified frame, bit, cycle and timeout values are in [ZGW_ELC_CAN_CONTRACT.md](ZGW_ELC_CAN_CONTRACT.md). Primary evidence is ZGW `APP/GatewaySwc/GatewaySwc.c::GatewaySwc_GenerateCanOutputs`, `BSW/Com/Com.c`, `BSW/Com/CanIf/CanIf.c`, `BSW/Com/CanNm/CanNm.c`, and `DB/ZGW_CAN_3.dbc`. ZGW does not define an ELC NM transmitter or a transceiver wake handshake. ELC's existing `CanH.c` uses PN1 bit 6 for its application traffic; the new state path retains this behavior and does not assign meaning to other PN bits.

### NM3 state machine and CanNm/CanSM/ComM

`ELC_APP/BSW/Com/CanNm/CanNm.c` now accepts only NM3 DLC 1, tracks WAIT_NM, NETWORK_REQUESTED, NETWORK_RELEASED and TIMED_OUT, and expires reception after 200 nominal 5 ms cycles. Valid NM3 with bit 6 set requests ELC application communication. A valid byte with bit 6 cleared releases it immediately; diagnostics do not extend the NM timer. `ComM.c` requests FullCom or RX-only and `CanSM.c` applies the application TX gate. `Can.c::Can_IsControllerOnline` also prevents FullCom when HAL is not listening or the bxCAN bus-off flag is set. `EcuM.c` remains in post-run when communication disappears, preserving CAN RX and a single existing-style post-run `Nvm_WriteAll` call; it no longer enters MCU standby solely because no NM3 was received. Hardware power and wake behavior are unverified.

### Command, feedback, Can/CanIf/Com

`CanIf` and `PduR` route ZGW LoadRequest `0x050` and VehicleState `0x3A0` to `Com`. `Com` validates the load data ID, CRC and DLC, validates the VehicleState nibble/value, and tracks both receive deadlines. `CanH` copies valid signals to the existing SMon and vehicle-status interfaces, clears the load command outside FullCom, and only reports missing application frames while FullCom is active. LoadStatus `0x051` and ELC telemetry `0x6EE`..`0x6F7` now pass from CanH/Com through PduR/CanIf/Can. COM buffers one latest frame per telemetry ID, checks DLC, drops pending application telemetry outside FullCom, and retries failed CAN submissions. `CanH` still determines the sampling cadence and builds measurement payloads; its XCP and diagnostic paths are still direct HAL users.

Invalid LoadRequest DLC/data ID/CRC now invalidates the prior command immediately. Invalid VehicleState invalidates the prior value; CanH clears its mirror to `0` when the signal is invalid or expired. After a valid frame, the missing-frame DTC threshold follows the 200-tick receive deadline instead of starting a second 200-tick wait. With no valid frame since FullCom entry, the DTC threshold is 201 ticks. The APP DCM programming-session gate reads the validated Com VehicleState directly, so an invalid frame cannot leave a previously mirrored value of `6` usable until the next CanH cycle. CanH's separate legacy `0x202` date/time decoder now checks standard data-frame type and at least four payload bytes. These are source-level safety checks, not measured bus timing.

ZGW DBC review found and corrected two concrete ELC feedback errors: `0x6F2` now carries coulomb SoC then OCV SoC, and `0x6F3` carries hybrid SoC then SoH. `0x6F7` is now one packed diagnosis byte. The ZGW boolean `Confindence` has no source-verified mapping from ELC's 0..100 `Confidence_pct`, so bit 2 is explicitly held at 0 pending a contract decision. Remaining flag bits follow the DBC. The `0x6F1`..`0x6F7` 200 ms ELC sampling cadence is retained; this differs from several ZGW DBC cycle attributes and needs a bus trace and gateway deadline check.

### CanTp/PduR/Dcm, Dem/NvM, FCD and FBL

PduR still has **no** CanTp route. ELC's existing APP DCM remains a raw `0x702/0x703` normal-address path in `BSW/Diag/Dcm/Dcm.c` and `CanH.c`; the FBL also uses that legacy transport. The required ZGW extended-address `0x710`, logical target `0x58` request and gateway-target `0xF0` response path is unimplemented. ISO-TP segmentation, P2/P2*, S3, asynchronous response pending, session/RID/DID configuration and ECU reset remain insufficient for the requested diagnostic architecture. ZGW `BSW/Com/CanTp/CanTp.c`, `BSW/Com/PduR/PduR.c`, `BSW/Diag/Dcm/Dcm.c` and `Dcm_Cfg.c` are the reference. Do not remove the legacy path until a replacement can execute the same ELC services and pass transport tests.

The legacy APP DCM received concrete defensive fixes while this route remains: `Dcm_main` no longer dispatches stale request bytes on every 5 ms cycle, and its programming-session branch now requires SID `0x10` as well as subfunction `0x02` and a currently valid VehicleState `6`. `CanH` checks the diagnostic CAN frame type and nonzero SF length/DLC before handing it to DCM; unsupported incoming FF/CF is rejected rather than misparsed as a service. A pending/busy guard keeps a later single frame from replacing the active request header and payload; flow-control frames still reach the ISO-TP TX hook. That ISR hook no longer clears the DCM's active request/response buffers; response-buffer clearing now happens when `Dcm_main` copies a new request. `Dcm_CanSendSF` and `can_tx8` now return a failed CAN submission instead of spinning forever on a full mailbox or bus-off. These fixes are **not** a complete CanTp/DCM migration and do not make routed diagnostics usable.

ELC `BSW/Diag/Dem/Dem.c` still owns the fixed event table and direct `Nvm_WriteBlock` persistence; `BSW/Nvm/Nvm.c` retains its existing memory format. ZGW `BSW/Diag/Dem/Dem.c`, `Dem_Cfg.c`, `BSW/Mem/Nvm/Nvm.c`, `BSW/Mem/MemIf/MemIf.c`, and `BSW/Sys/Crc/Crc.c` have not been adapted. No flash writes or restore tests were performed. FBL and RAM updater source from the earlier revision was preserved; no new claim about self-update recovery is made.

FCD `FCD.pyw` uses `ROUTINE_SELECT_SW_BLOCK=0x0200`, `ROUTINE_START_FBL_RAM_UPDATER=0x0155`, `ROUTINE_ERASE_MEMORY=0x0001` and optional CRC RID `0x0002` in `_execute_payload` and `_simulated_flash_request_sequence`. The exact proposed FCD patch is an ELC target profile selected by logical address `0x58` in those functions: map APP/FBL selection, enter updater, erase, CRC and reset to documented ELC RIDs only after matching ELC handlers and negative cases exist; cap transfer chunks at the ELC `0x74` response limit; correlate a real response from `0x710`/EA `0xF0` before marking a routed request successful. The exact proposed ZGW patch, if the gateway cannot forward the selected ELC transport, is in `ParallelFlashSwc_ForwardCodingRequest`/`CanTp_TransmitExtendedAddressInternal`: keep `0x58` routing but require physical ECU response/flow-control confirmation instead of synthetic acknowledgement for ELC. Neither repository was edited.
